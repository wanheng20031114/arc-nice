# 塔防模式实战性能评估

日期：2026-07-17  
Godot：4.6.3 stable  
测试机渲染：D3D12 / Forward+ / Intel UHD Graphics 770  
真实窗口：1280×720，游戏 Viewport 1152×648，60 FPS 上限

## 目标与测量口径

本评估不把“批量实例化空节点”当作塔防压力。生产场景中的地图、共享
`GridPathfinder`、敌人场景、目标切换、玩家/基地、物理碰撞、弹体与特效池、
音频限流、镜头和渲染链均保持工作。测试分为以下几层：

1. 波次生成与 300 敌人硬上限、1200 敌人长波生命周期。
2. 300 活敌 + 64 玉米机枪 + 32 龙舌兰炮的综合交战。
3. 每种敌人独立投入生产塔防场景，分别测接近、交战或一次性爆发阶段。
4. 正式 WaveConfig 混合、视觉热点 A/B、Physics2D 隔离和长生命周期回收。

监控不依赖人工盯编辑器 Profiler：Godot 内部逐帧读取 `Performance` 与
`RenderingServer` 的脚本、物理、碰撞、节点、内存、渲染 CPU/GPU、Draw Call
等监视器；`Enemy` 的导航、前视、`test_move`、`move_and_slide`、接触伤害另有
微秒级分段累计；运行时遥测记录活敌与弹体峰值；外部采样真实 `Godot.exe`
的 CPU、Working Set、Private Bytes、线程和句柄。该方案比一次人工 Profiler
截屏更适合固定种子、批量复跑和前后对照。

相关入口：

- `dev_tools/tower_defense_enemy_cohort_performance_probe.gd`
- `dev_tools/run_tower_defense_enemy_cohort_probe.ps1`
- `dev_tools/game_tower_defense_combined_horde_turret_stress_probe.gd`
- `dev_tools/runtime_performance_telemetry_smoke_test.gd`

## 已完成基线

### 分阶段预热与 300 敌人生成

首次冷运行的分阶段预热出现 93.171 ms 单帧并触发既有 75 ms 门槛；紧接着两次
复跑分别为 15.535 ms 和 16.031 ms。说明冷导入/缓存仍可能造成一次明显尖峰，
但稳定预热过程本身没有持续复现 75 ms 以上卡顿。

预热完成后的 300 敌人生成阶段两次复跑：

| 指标 | 复跑 1 | 复跑 2 |
|---|---:|---:|
| 帧时间 p95 | 10.121 ms | 9.938 ms |
| 帧时间 p99 | 10.918 ms | 11.334 ms |
| 四敌人生成批次 p95 | 1.080 ms | 1.096 ms |
| 四敌人生成批次最大值 | 1.295 ms | 1.226 ms |

### 300 活敌 + 96 防御塔综合交战

配置：240 基础原石虫、60 硬壳原石虫、64 玉米机枪、32 龙舌兰炮。真实索敌、
射线、伤害、弹体、受击特效池、玩家移动、共享寻路和镜头同时工作。

| 指标 | 结果 |
|---|---:|
| 帧时间 p50 | 13.976 ms |
| 帧时间 p95 | 20.919 ms |
| 帧时间最大值 | 21.161 ms |
| 物理时间 p50（移动阶段） | 5.628–5.679 ms |
| 物理时间 p95（移动阶段） | 20.062–20.321 ms |
| 碰撞对 p50 / p95 | 约 3311 / 3373 |
| 64 塔真实索敌扫掠 p95 | 4.887 ms |
| 64 塔同步锁定帧额外 p95 | 7.934 ms |
| 稳定节点数 | 6274 → 6266（无增长） |
| 龙舌兰弹体池 | 无溢出、无丢弃、最终全部归还 |
| 敌人受击特效 | 容量 128，主动丢弃累计 12087 次 |

结论：这一实战密度的中位帧仍在 16.67 ms 内，但 p95 已明显不能稳定保持 60
FPS。GPU 并非主要嫌疑；同帧批量索敌/开火和高碰撞密度是当前更直接的容量点。
受击特效池没有泄漏，但高压下大量反馈被有意丢弃，画面反馈会发生明显降级。

## 逐敌人 300 数量接近阶段：第一批

所有案例使用同一地图、位置算法、固定种子、60 帧预热和 180 帧采样。敌人由
生产目标分配逻辑决定追玩家或冲基地；因此“结束存活数”下降表示真实冲线/退出，
不是测试清理。`>18 ms` 比例用于避开 Windows 60 Hz 定时器围绕 16.667 ms 的
正常微抖，p95/p99 仍是主要判据。

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 基础原石虫（复跑） | 289 | 16.617 | 18.549 | 22.509 | 22.789 | 5.6% | 0.866 | 1.848 ms | 0 |
| 迅捷原石虫 | 263 | 16.657 | 18.170 | 19.343 | 19.606 | 6.7% | 0.854 | 1.737 ms | 0 |
| 硬壳原石虫 | 288 | 16.647 | 18.190 | 19.373 | 20.159 | 6.1% | 0.906 | 1.870 ms | 0 |
| 火焰弹原石虫 | 286 | 16.691 | 17.730 | 20.721 | 22.255 | 5.0% | 0.930 | 1.756 ms | 46 |

补充观察：

- 基础型两次完整运行的 p95 为 18.467 / 18.549 ms，较稳定；p99 为 19.530 /
  22.509 ms，说明少量尾部尖峰仍有明显运行间方差。复跑中 `>18 ms` 为 5.6%。
- 基础型外部进程峰值：Working Set 533–537 MiB、Private Bytes 464–468 MiB、
  整机归一化 CPU 峰值 5.23–5.35%。
- 第一批其余三类的 Working Set 峰值约 535–536 MiB、Private Bytes 466–467 MiB，
  没有随类型出现持续内存增长。
- 火焰弹型结束时仍有 11 个在途池化弹体，池无溢出、无丢弃；这是活跃战斗状态，
  不是生命周期泄漏。
- 火焰弹型的 p95 不高于纯移动型，但 p99/最大值更差，说明弹体齐射带来稀疏尖峰。
- 当前四类 GPU p95 全部低于 1 ms，逐敌人接近阶段仍是 CPU/物理主导。

## 测量风险与判读规则

1. 原生 `Performance.TIME_PHYSICS_PROCESS` 在很短的冷窗口会保留上一更新周期的
   高值，不能单独用作每帧百分位；报告以墙钟、分段累计和渲染服务器计时交叉验证。
2. 基础型已经复跑；p95 稳定而 p99 有运行间方差，因此类型排序不使用单个最大帧。
3. 60 FPS 的 Windows 帧节奏会在 16.667 ms 两侧自然摆动，`>18 ms` 与 p95/p99
   比简单统计 `>16.667 ms` 更能表示真正错过刷新。
4. `GameTowerDefense` 的正式配置明确 `linglan_boss_enabled=false`，塔防战役也不含
   Boss step；铃兰不纳入塔防活跃敌人容量结论，不能用强行放入塔防地图的结果冒充
   实战数据。

寻路。即使如此，GPU p95 仍低于 3 ms，当前整帧的首要容量仍在 CPU/物理侧。

## 翠壳与守护者 VFX A/B

完整 A/B 使用 300 个冻结但保留作者视觉/Area 的敌人同屏密集排列，消除移动和
寻路差异。修正后的完整套件已通过，粒子关闭会同时设置 `visible=false`，守护者
测试也不再引用已经从场景删除的旧 `AuraArea`。

### 翠壳

| 状态 | Draw Call | GPU p95 | Render CPU p95 | Render objects | Primitives |
|---|---:|---:|---:|---:|---:|
| 完整视觉 | 959 | 2.639 ms | 1.415 ms | 1400 | 40938 |
| 关闭粒子、保留范围线 | 360 | 1.174 ms | 0.953 ms | 1100 | 21738 |
| 保留粒子、关闭范围线 | 659 | 2.350 ms | 1.199 ms | 1100 | 25938 |
| 粒子和范围线都关闭、保留 Area | 60 | 0.867 ms | 0.705 ms | 800 | 6738 |

300 个粒子发射器约占 599 Draw Call 和 1.47 ms GPU p95；300 条范围线约占 300
Draw Call 和 0.29–0.31 ms GPU。Area 保留时碰撞对始终为 42，说明主要热点是

不支持为了 300 同类边界而全局删除视觉，但适合增加“同屏密度预算”作为后续优化。

| 生产灯光预算 | 12 | 6.551 ms | 18.457 ms | 77 |

## 阶段性结论（未含正式混合塔阵）

1. 300 活敌的共享寻路稳定成本约 1.7–2.3 ms/帧，是持续 CPU 基线，但没有发现
   单一兵种触发的超线性导航增长。
2. 300 敌人 + 96 塔的综合交战 p95 为 20.919 ms，是目前最接近实际玩法且明确
   超出稳定 60 FPS 的场景；热点在高碰撞密度与同帧塔索敌/锁定，而非 GPU。
3. 真实混合波单独运行的 p95 为 17.48–18.14 ms；复杂远程池均保持语义完整，
   没有泄漏或关键弹体丢弃。
4. 视觉最大风险是守护者灯光重叠，其次是翠壳粒子/范围线的 Draw Call；现有真实
   配比尚可，但极端同屏聚集会显著侵占 GPU 余量。
5. 同步 64 玉米塔锁定增加约 7.93 ms 是故意构造的相位最坏情况；生产放置时间与
   当前压力探针的黄金比例起始偏移会自然错峰，不能直接当作每秒必现卡顿。
6. 铃兰在塔防配置中禁用。强行放入塔防地图会在标准 Boss 技能坐标与塔防水域/
   静态体之间产生不可达移动，这属于无效夹具，不进入塔防性能排名。

## 长稳与热点归因补充

### 1200 敌人完整生命周期

正式长波队列以四个 300 敌人 tranche 生成、击败、补充并结算：1200/1200 均完成，
最终息壤奖励 2730 与逐配置期望完全一致。批量 `_die` 循环 p95/最大值 6.950 ms；
80 个延迟清理帧 p95 16.808 ms、最大 17.007 ms。最坏清理帧仍保持 300 活跃敌人
（旧批退出的同时新批补位），节点数 427→427，没有跨 tranche 增长。

### Physics2D 隔离 A/B

300 个真实移动敌人、两次反向顺序采样的合并结果：

| 模式 | Physics p50 | p95 | 与完整模式差值 |
|---|---:|---:|---:|
| 完整脚本、Body、接触 Area | 9.683 ms | 11.117 ms | — |
| 脚本关闭，Body/Area 保留 | 0.111 ms | 0.282 ms | -9.572 ms |
| 移动保留，接触 Area 关闭 | 7.952 ms | 9.712 ms | -1.731 ms |
| 接触 Area 保留，尽量走验证直线 | 8.931 ms | 9.399 ms | -0.752 ms |

结论是脚本驱动的导航、运动提交与接触更新构成主要持续成本。扩大直线运动证书的
剩余收益有限；接触 Area 在 300 数量约占 1.7 ms，但它同时承担玩家/植物进入、
停步、植物移除与接触伤害语义，不能仅为跑分关闭。96 塔综合场景中的碰撞对约
3312–3501，表明未来若要继续优化，应设计集中式植物接触索引并做严格行为 A/B，
而不是改碰撞层让敌人穿过建筑。

### 玉米塔与综合场景复跑

128 权威塔 + 128 代理塔、300 冻结目标的独立微基准：两次 128 塔索敌为
6.593/6.189 ms；768 条权威 hitscan+伤害为 9.947 ms；代理只播放视觉为 4.798 ms，
节点恒定 6453。

300 敌人 + 96 塔综合实机复跑与首轮高度一致：

- 稳定错峰战斗墙钟 p50 13.958–13.960 ms，p95 20.933–20.941 ms，最大 21.089 ms；
- 玩家移动相对静止 p50 只增加 0.002 ms，移动并非当前热点；
- 64 塔真实索敌批次 p95 4.990 ms，全部走最近可见目标快路径；
- 64 塔故意同步时锁定帧相对普通帧增加 7.490 ms（首轮 7.934 ms）；
- 单次 64 塔阶段归因：射线 0.430 ms、视觉 0.452 ms、无粒子伤害 0.550 ms、
  受击粒子 1.470 ms、音频请求 0.533 ms；
- 节点 6274→6266，龙舌兰弹体全归还；受击特效最终归还但主动丢弃 12081 次。

综合场景已重复稳定复现，因此 20.9 ms p95 不是一次冷缓存噪声。优化优先级应是
减少塔同帧索敌和密集植物接触成本，其次才是已较小的单发射线或玩家移动。

## 正式 WaveConfig + 96 塔实战压力

最终综合夹具直接加载第 12 波正式资源，按作者配比精确缩放到 300 个同时活跃敌人，
并放置 64 座正式玉米机枪和 32 座正式龙舌兰炮。塔通过作者场景实例化，保留真实
计时器、索敌、射线、伤害、弹体、音频和对象池；塔的初始攻击相位按黄金比例错开，
模拟玩家逐步建塔后的自然相位，而不是把 64 座塔故意同步。固定种子、60 帧预热、
240 帧采样的 60 FPS 窗口结果如下：

| 复跑 | p50 | p95 | p99 | 最大 | `>33.333 ms` |
|---|---:|---:|---:|---:|---:|
| 1 | 16.741 ms | 25.651 ms | 34.094 ms | 82.296 ms | 5 / 240 |
| 2 | 16.730 ms | 26.279 ms | 35.935 ms | 108.390 ms | 5 / 240 |
| 3 | 17.020 ms | 25.765 ms | 36.085 ms | 118.309 ms | 4 / 240 |
| 4（慢帧关联采样） | 16.830 ms | 26.274 ms | 32.472 ms | 104.659 ms | 2 / 240 |

四次 p95 只跨 0.63 ms，说明 25.7–26.3 ms 的重载尾部可重复；单次最大帧则在
82–118 ms 之间漂移。GPU p95 稳定在约 3.09 ms，碰撞对 p50/p95 约为
3448/3511。每个四秒窗口约执行 317 次玉米索敌锁定、1900 条 hitscan，并主动
丢弃约 2000 次容量受限的敌人受击特效；龙舌兰、AK、SMG、RPG、法师等关键弹体
池都没有丢弃或溢出。外部进程 Working Set / Private Bytes 峰值约 728 / 650 MiB，
没有随复跑增长。

第 5 波使用同样 300 敌人 + 96 塔时，p50/p95/p99 为
16.359/23.461/31.100 ms，最大 121.192 ms，GPU p95 2.721 ms，碰撞对 p50/p95
2740/2761。第 12 波稳定尾部更重，符合其 Capoo 技能、远程弹体和更高植物接触
密度；这也证明只测 300 个基础敌人会低估正式后期波次。

### 关闭帧率节拍的因果对照

`--max-fps=0` 会同时解除 Engine 上限并显式关闭 VSync。第 12 波 + 96 塔在 300 帧
窗口中得到 p50/p95/p99 = 16.931/26.339/36.752 ms、最大 97.515 ms；GPU p95
3.122 ms、碰撞对 p50/p95 3446/3500、394 次锁定和 2370 条射线。结果与四次
60 FPS 复跑一致，因此约 17 ms 中位和约 26 ms p95 是实算压力，不是等待刷新。

同波次 300 敌人、无塔、同样解除上限的控制组为 p50 15.555 ms、p95 21.862 ms、
p99 25.887 ms、最大 31.876 ms，GPU p95 1.539 ms，碰撞对 p50 只有 31。控制组
确实突破 16.667 ms，验证了无 VSync 测量有效；96 塔使碰撞对上升两个数量级，
并把稳定尾部再推高约 4.5 ms。

### 慢帧关联判读

第四次复跑记录了最慢八帧的锁定、射线、特效丢弃、CombatTargetIndex 大小、
物理活跃对象、碰撞对和 GPU：

- 104.659 ms 最慢帧只有 1 次锁定、27 条射线、30 次受击特效丢弃，目标索引大小
  未变化，GPU 2.102 ms；并非索引重建、玉米齐射或 GPU 峰值。
- 43.237 ms 帧同样只有 1 次锁定、12 条射线和 10 次特效丢弃。
- 其余 31–32 ms 尾帧为 1–6 次锁定、15–20 条射线，没有共同的单帧事件阈值。
- 解除 VSync 后仍出现一个 97.515 ms 孤立帧，说明这类约 100 ms 极端尾帧不由
  60 Hz 等待单独解释。

因此目前有充分证据把稳定 p95 归到 CPU/Physics2D 与塔战斗密度，但没有证据把
漂移的约 100 ms 单帧归到某一条游戏逻辑。它更像 Windows 调度、驱动提交或冷
资源路径一类外部/低频尾延迟，仍需 ETW/GPUView 等系统级跟踪才能精确归因。
Godot 的 `TIME_PROCESS` / `TIME_PHYSICS_PROCESS` 在短窗口中还会以较粗周期更新，
报告没有用它们单独给最慢帧定罪。

## 问题清单与优化优先级

### P0：明确容量结论

当前 Intel UHD 770 测试机上，“正式第 12 波比例 + 300 活敌 + 96 塔”不满足稳定
60 FPS：p50 已约 16.9 ms，p95 约 26 ms，p99 约 32–37 ms。稳定 30 FPS 的大部分
帧可满足，但每个四到五秒窗口仍可能有 2–5 帧超过 33.333 ms，另有低频约
100 ms 尾帧。若 300/96 是必须同时达到的产品硬上限，应把它作为持续回归门槛；
若 60 FPS 是硬目标，则当前不能判定通过。

### P1：优先处理 CPU/Physics2D 接触结构

300 敌人下关闭接触 Area 可回收约 1.7 ms，综合塔阵又出现约 3500 碰撞对。这是
最有希望的持续 CPU 优化方向，但接触 Area 同时承载玩家/植物进入、停步、植物
移除和接触伤害，不能直接关层或删节点。建议下一步设计集中式植物接触索引，逐项
对照这些语义后再替换；这次没有为跑分改动生产碰撞逻辑。

### P1：限制同屏战斗提交，而非重复重写最近目标查询

现有 `CombatTargetIndex` 已把 32 塔索敌从旧扫掠的 3.267 ms 降至 1.978 ms，最近
可见目标快路径单次基准约 0.516 ms。生产建塔的计时器相位也天然错开；继续优化应
考虑每物理帧的索敌/开火预算或按空间桶分摊提交，并验证伤害时序，而不是恢复全表
扫描。故意同步 64 玉米塔会额外增加约 7.49 ms，说明预算化仍有防极端相位的价值。

### P1：给守护者灯光提供质量预算

300 守护者密集同屏时，生产 12 灯比全关增加约 4.85 ms GPU；预算 12→8 可回收
约 1.60 ms。正式混合波目前 GPU 不是首要瓶颈，所以不应无条件降画质，但建议把
最大活动灯数做成图形质量选项，并按屏幕覆盖而非敌人总数分配。

### P2：按同屏密度降级翠壳与命中特效

翠壳 300 同类时粒子约占 599 Draw Call / 1.47 ms GPU，范围线约占 300 Draw Call /
0.30 ms GPU。综合塔阵的敌人受击特效池每四秒主动丢弃约 2000 次，逻辑正确但反馈
明显降级。建议以可见密度、距离和最近命中时间做 LOD，并记录“请求数/呈现数”质量
指标；不要通过无限扩池换取瞬时画面完整性。

### P2：把冷启动与约 100 ms 外部尾帧分开治理

首次资源预热曾有 93.171 ms，热复跑降至 15–16 ms，适合通过加载阶段预热管线与
关键资源控制。战斗中跨复跑漂移的 82–121 ms 单帧没有与某类战斗事件相关，应先
做系统级 trace；在拿到证据前堆叠空判断、延迟分支或扩大对象池只会掩盖问题。

## 最终结论

逐个敌人 300 数量、正式混合波、96 塔交战、集中火力、同步爆炸、视觉 A/B、
Physics2D 隔离和 1200 敌人完整生命周期均已覆盖。没有发现关键弹体丢失、池泄漏、
节点跨波增长、同步死亡二次复杂度或单一敌人脚本失控；铃兰在正式塔防配置中禁用，
因此没有用无效 Boss 夹具污染结论。

真正的容量问题是：300/96 后期实战在本机已经越过稳定 60 FPS，CPU/Physics2D
和密集植物接触是第一优先级，塔战斗提交是第二个可预算化热点；守护者灯光与翠壳
视觉是可配置的 GPU 风险。当前生产代码未被冒险修改，修正的是性能探针本身的过期
Guardian 假设和粒子关闭口径，确保后续回归可重复、可比较。
