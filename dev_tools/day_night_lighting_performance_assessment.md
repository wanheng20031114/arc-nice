# 昼夜与局部灯光性能评估

测试日期：2026-07-20
Godot：4.6.3 stable，D3D12 Forward+
GPU：NVIDIA GeForce RTX 3080
固定测试环境：1152×648、VSync 开启、60 FPS 上限

## 结论

- 当前局部灯数量不会形成明显的 CPU 压力。`DayNightController` 和
  `NightPointLight2D` 都没有 `_process` 或 `_physics_process`；稳定白天和
  稳定夜晚没有逐帧脚本更新，只有 5 秒昼夜渐变期间会逐帧广播亮度因子。
- 白天会把所有昼夜灯置为 `enabled=false`、`energy=0`，不提交局部灯绘制。
  延长至 5 秒只增加渐变持续帧数，不增加每帧需要更新的灯数量。
- 植被桩、竹筒迫击炮、植物培育中心和每名玩家都各自最多使用 1 个昼夜灯。
  培育中心的 5 个嫩绿色亮点合并在一张光照纹理中，共用 1 个
  `NightPointLight2D`，没有为 5 个亮点分别注册信号回调。
- 多人植物建筑上限为 256。按 256 座各 1 灯、最多 8 名玩家和塔防场景 7 盏
  固定灯估算，最坏约为 271 个昼夜灯订阅者。单机可放置区的理论上限为
  `22 × 18 = 396` 格，加 1 名玩家和 7 盏固定灯约为 404 盏。512 灯 CPU
  微基准覆盖了这两个上界。
- 真实渲染的 256 灯压力测试中，两次完整 5 秒渐变的 Render CPU p95 最高为
  `0.765 ms`，GPU p95 最高为 `0.900 ms`；密集稳态的 Render CPU/GPU p95
  分别为 `0.718/0.319 ms`。结果通过探针的全部预算断言。
- 压力灯使用 `texture_scale=0.82`、`energy=0.62`，高于实际植被环灯的
  `0.52/0.38` 和培育中心热点灯的 `0.25/0.20`，因此是偏保守的覆盖面积与
  能量测试。

## 已执行的 CPU 优化

1. `NightPointLight2D` 在渐变中仍更新实际 `energy`，但只在跨过亮灭阈值时
   才写入 `enabled`。这样保留连续渐变，同时避免每盏灯每帧重复向
   RenderingServer 写入相同的启用状态。
2. `DayNightController` 只在昼夜因子实际变化时广播全部灯。首次 `_ready`
   仍强制广播一次以保持组件兼容；重复设置相同终点，以及 Tween 完成回调
   再次写入同一终点时，不再产生 O(N) 回调。
3. `NightPointLight2D.set_night_energy()` 对完全相同的能量值直接返回，避免
   状态事件重复刷新。

同进程 A/B 基准同时实例化 512 盏优化灯与 512 盏旧行为灯，并交替两组的
执行先后顺序。旧行为夹具完整保留了每次广播都写 `energy/enabled` 的路径。

| 512 灯场景 | 优化版总耗时 | 旧版总耗时 | 优化版 p95 / max | 旧版 p95 / max | 总耗时降幅 |
|---|---:|---:|---:|---:|---:|
| 因子持续变化 | 278.009 ms | 307.170 ms | 0.920 / 1.295 ms | 1.009 / 1.651 ms | 9.49% |
| 重复相同因子 | 0.768 ms | 200.860 ms | 0.005 / 0.010 ms | 0.554 / 0.869 ms | 99.62% |

“因子持续变化”对应正常昼夜渐变，主要量到避免重复 `enabled` 写入的收益；
“重复相同因子”对应重复状态调用和 Tween 终点重复应用，量到跳过整批信号的
收益。优化前后每盏灯的 `enabled/energy` 状态均由探针逐一比对一致。

## 256 灯真实渲染诊断

以下是最终代码的同一次运行结果。固定场景本身有 8 盏灯，因此夜间总计
264 盏；探针会断言 256 盏压力灯都处于相机可见范围。

| 阶段 | 活跃灯 | Wall p95 | Render CPU p95 | GPU p95 |
|---|---:|---:|---:|---:|
| 初始白天 | 0 | 16.923 ms | 0.562 ms | 0.122 ms |
| 玩家与门夜灯 | 8 | 16.918 ms | 0.502 ms | 0.271 ms |
| 256 个分散绿环 | 264 | 16.734 ms | 0.590 ms | 0.534 ms |
| 256 个密集绿环 | 264 | 16.739 ms | 0.718 ms | 0.319 ms |
| 夜→昼 5 秒渐变 | 动态 | 16.840 ms | 0.652 ms | 0.900 ms |
| 返回白天 | 0 | 18.614 ms | 0.975 ms | 0.074 ms |
| 昼→夜 5 秒渐变 | 动态 | 16.804 ms | 0.765 ms | 0.205 ms |

夜→昼测试期间有一次 `109.597 ms` 的 Wall 调度离群值，因此该段记录为
294 帧、4978.260 ms；同一帧 Render CPU/GPU 最大值仅为
`1.238/0.980 ms`，且 Wall p95 仍为 `16.840 ms`，不属于灯光渲染造成的
持续卡顿。反向渐变为 301 帧、5007.224 ms。

Wall 时间受 60 Hz VSync 和系统调度影响，因此判断灯光开销时以 Render
CPU/GPU 及 p95 为主。返回白天后活跃灯数量归零，Draw Call 回到初始白天值。

## 当前策略

现阶段无需为局部灯增加逐帧距离检测、动态创建/销毁或每灯 Tween；这些方案
反而会增加 CPU 管理成本。继续保持“每座植物建筑最多 1 个昼夜灯”即可。
若未来扩大光照纹理、开启阴影，或提高单机可同时放置的建筑上限，应重新运行
探针；届时优先根据屏幕覆盖面积与重叠量评估 GPU，再根据订阅灯数量评估 CPU。

## 复现命令

正式样本必须使用真实渲染驱动，不能添加 `--headless`：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648
```

256 灯上限诊断：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648 `
  -- --lights=256 --warmup=20 --samples=60 --micro-samples=500
```

需要人工检查一次分散灯布局时，可在 `--` 后追加 `--screenshot`。截图写入
`user://day_night_lighting_probe.png`，不会污染 Git 工作区。

探针内置以下回归门槛：

- 默认 100 灯 Render CPU p95 增量不超过 `0.5 ms`；
- 默认 100 灯 GPU p95 增量不超过 `1.0 ms`；
- 默认 100 灯渐变 Render CPU/GPU p95 增量分别不超过 `1.0/1.5 ms`；
- 超过 100 灯的诊断渐变 Render CPU/GPU p95 增量分别不超过
  `2.0/4.0 ms`；
- 100/256 灯 Wall p95 不超过 `20 ms`；
- 512 灯优化版广播 CPU p95 不超过 `1 ms`、最大不超过 `2 ms`；
- 两个 A/B 阶段的优化版总耗时不得比旧版差 5% 以上；
- 每段默认 5 秒渐变不得早于 `4.8 秒` 完成；
- 返回白天后全部灯关闭，Draw Call 回到初始白天的 ±1。
