# 昼夜与局部灯光性能评估

测试日期：2026-07-20
Godot：4.6.3 stable，D3D12 Forward+
GPU：NVIDIA GeForce RTX 3080
固定测试环境：1152×648、VSync 开启、60 FPS 上限

> 2026-07-23 新增两盏NPC常驻夜灯后，数量上界与探针契约已同步更新；下方
> D3D12长样本仍是新增前的8盏固定灯历史基线，尚未重跑10盏固定灯实渲染证书。
>
> 2026-07-29 竹筒迫击炮增加一盏仅在预热和开火阶段启用的炮口灯。它占
> 2×2 格、每座共两盏灯，因此单位占格密度仍低于 1×1 单灯建筑；更新后的
> 单机与多人理论上界仍在既有 512 灯 CPU 基准覆盖范围内。本次未重新采集
> 炮口阶段的 D3D12 实渲染长样本，不能把数量覆盖等同于新增光效的实渲染证书。

## 结论

- 当前局部灯不会形成明显的持续 CPU 压力。`DayNightController` 和
  `NightPointLight2D` 都没有 `_process` 或 `_physics_process`；稳定白天和
  稳定夜晚没有逐帧灯光脚本回调。
- 只有 5 秒昼夜渐变期间存在一条控制器 Tween，并按变化后的昼夜因子向灯光
  广播。512 灯最终实测广播 p95 为 `1.079 ms`，而生产场景理论上界为
  418 灯；按灯数保守换算约为 `0.881 ms`，且只持续于昼夜切换。
- 白天会把所有昼夜灯置为 `enabled=false`、`energy=0`。建造中、拆除中、
  玩家死亡等不可发光状态也会关闭灯，并跳过保持为零的重复能量写入。
- 1×1 植物建筑每座最多使用 1 个昼夜灯。2×2 的竹筒迫击炮使用状态灯与
  阶段性炮口灯共 2 盏，绣球花雨塔也使用 2 盏阶段灯；两者单位占格均为
  0.5 盏。培育中心与科研中心的多个热点分别合并在一张纹理中，没有为每个
  亮点创建独立 `PointLight2D`。
- 所有 `NightPointLight2D` 明确关闭阴影；项目内没有
  `LightOccluder2D`、`OccluderPolygon2D` 或 `shadow_enabled=true`。
  当前不存在 2D 灯光阴影带来的额外 CPU 几何提交成本。
- 灯光纹理通过场景外部资源共享；运行时不会为热点复制纹理或材质。科研中心
  边框噪波使用 shader `TIME` 在 GPU 上执行；研发进度只跟随现有的
  `0.25 s` 权威研究事件更新，不运行逐实例进度 Tween。
- 96 个真实敌人保持移动、碰撞和寻路的实战样本中，昼夜渐变 Render CPU
  p95 最高为 `0.852 ms`，稳定夜间为 `0.589 ms`。实战样本没有出现灯光
  生命周期错误或敌人数量下降。

## 数量上界

塔防场景固定包含 7 盏门灯与 2 盏NPC灯；每名玩家各 1 盏灯。1×1 发光建筑
每座 1 盏；2×2 的竹筒迫击炮与绣球花雨塔每座 2 盏。守卫原石虫使用独立的
原生 `PointLight2D`，生产预算最多同时启用 12 盏。

| 场景 | 建筑灯 | 玩家灯 | 固定门灯 | NPC灯 | 守卫灯预算 | 理论总数 |
|---|---:|---:|---:|---:|---:|---:|
| 多人团队上限 | 302 | 8 | 7 | 2 | 12 | 331 |
| 单机 22×18 全部 1×1 建筑 | 396 | 1 | 7 | 2 | 12 | 418 |

多人上界同时受 256 座团队建筑上限与 396 个可用格约束：若用 `x` 表示
1×1 单灯建筑、`y` 表示 2×2 双灯建筑，则 `x+y≤256`、`x+4y≤396`，
`x+2y` 最大为 302。单机纯 1×1 建筑仍以每格 1 盏形成更高的 396 盏建筑灯
上界。512 灯 CPU 微基准覆盖了两个理论上界。科研中心占 2×2 格，因此即使
单机区域全部放置科研中心，研发期间也最多有 99 个外框以 4 Hz 事件频率各
写入一个进度参数；不存在逐帧脚本插值。

## CPU 路径审计

### 稳定状态

`NightPointLight2D` 只在 `_ready` 时延迟查找一次祖先
`DayNightController`，连接一次 `night_factor_changed`，离树时断开。
绑定完成后不扫描场景树、不轮询距离，也没有单灯 Tween。白天灯光禁用；
夜间保持固定能量时也没有脚本更新。

`DayNightController` 只在状态切换时创建一条 Tween。默认 5 秒渐变约产生
300 次因子变化广播，不随帧率以外的频率另建定时器。

### 建筑状态

- 植被桩在建造、完成和拆除事件中切换环灯许可，灯节点保持常驻。
- 竹筒迫击炮的状态格与炮口灯都只在动画帧或网络状态事件变化时更新；炮口灯
  在待机、建造、拆除和白天保持禁用，不创建逐帧回调或独立 Tween。
- 培育中心与科研中心只在生命周期事件中切换热点灯。
- 科研中心研发边框复用研究协调器已有的 4 Hz 权威状态事件，每次只更新一个
  实例 shader 进度参数。60 秒研究正好约 240 步，接近 32×32 两像素外框的
  路径像素数；无需为每座建筑创建逐帧进度 Tween。
- 玩家只在准备完成、死亡和复活事件中切换夜灯许可。
- 两位NPC复用玩家柔光，并只在自身激活/隐藏事件中切换夜灯许可。

### 守卫原石虫

每只守卫场景预置一盏原生 `PointLight2D`，但最多 12 盏启用。300 只守卫
探针中，完整场景创建耗时 `133.092 ms`，生产预算仍只启用 12 盏，短窗口
Render CPU/GPU p95 为 `0.869/0.327 ms`。

释放一个守卫灯预算时，会延迟通知候选组尝试接替。活跃灯数有 12 的硬上限，
正常波次风险较低；若未来出现数百只守卫在同一帧集中死亡，候选组通知会形成
一次 O(守卫数) 的短暂 CPU 突发，应在那种新负载下重新测量。

## 已执行的 CPU 优化

1. `NightPointLight2D` 只在跨过亮灭阈值时写 `enabled`，保留连续渐变但避免
   重复提交相同启用状态。
2. `DayNightController` 只在昼夜因子实际变化时广播。首次 `_ready` 仍强制
   广播一次；重复终点调用和 Tween 完成后的同值写入不再触发 O(N) 回调。
3. `NightPointLight2D.set_night_energy()` 对相同能量直接返回。
4. `NightPointLight2D` 只在实际能量变化时写 `energy`。建造、拆除或死亡等
   禁止发光状态在整个 5 秒渐变中保持零能量，不再重复向 RenderingServer
   写入零值。
5. 灯节点采用常驻开关，不在建筑状态变化时动态创建和销毁。

## 512 灯广播 A/B

同进程 A/B 基准同时实例化 512 盏优化灯与 512 盏旧行为灯，并交替两组执行
顺序。旧行为夹具完整保留每次广播都写 `energy/enabled` 的路径。以下为最终
代码、500 次采样的同一次 D3D12 运行：

| 512 灯场景 | 优化版总耗时 | 旧版总耗时 | 优化版 p95 / max | 旧版 p95 / max | 总耗时降幅 |
|---|---:|---:|---:|---:|---:|
| 因子持续变化 | 362.206 ms | 394.668 ms | 1.079 / 1.532 ms | 1.186 / 1.671 ms | 8.23% |
| 重复相同因子 | 1.697 ms | 307.294 ms | 0.010 / 0.080 ms | 0.997 / 1.146 ms | 99.45% |
| 禁止发光时因子变化 | 313.869 ms | 352.014 ms | 0.948 / 1.396 ms | 1.019 / 1.888 ms | 10.84% |

禁止发光路径相较优化版正常渐变又减少 `13.35%` 总耗时，直接证明保持零能量
时已经跳过冗余写入。每个阶段均逐灯比对 `enabled/energy`，优化版与旧路径
状态一致。

512 灯绝对 p95 诊断门槛设为 `1.25 ms`，max 门槛仍为 `2 ms`，A/B 总耗时
仍不得比旧版回退 5% 以上。此前在用户 Godot 编辑器与探针并行时，两次测得
`1.195 ms` 和 `1.004 ms`，旧的 `1.000 ms` 门槛会因 4 微秒级调度噪声
误报。改为 1.25 ms 是为容纳并行编辑器和系统调度噪声，不是放宽生产预算；
实际生产上界只有 418 灯。

## 常驻开关与节点抖动

生命周期基准每轮处理 128 盏灯，共 24 轮，并验证节点数与信号连接数没有
泄漏：

| 操作 | 每批 p95 | 每灯 p95 |
|---|---:|---:|
| 常驻灯关闭后再开启 | 0.526 ms | 4.109 μs |
| 实例化并加入场景树 | 3.065 ms | 23.945 μs |
| 查找祖先并连接信号 | 0.728 ms | 5.688 μs |
| 断开并释放节点 | 1.433 ms | 11.195 μs |

一次完整创建、绑定、销毁合计 p95 为 `5.226 ms/128 灯`，约为常驻开关的
`9.94 倍`。因此当前“场景内预置灯节点、生命周期只切换许可”的设计优于
运行时反复创建和销毁。

## 96 敌人实战样本

`--live-gameplay` 使用第一波真实敌人场景，保留 96 个敌人的物理移动、碰撞、
寻路和生产游戏脚本；只停止继续生成敌人的计时器。暖机后敌人数量在整个样本
中保持 96。

| 阶段 | Wall p95 | Render CPU p95 | GPU p95 | Process p95 | Physics p95 |
|---|---:|---:|---:|---:|---:|
| 昼→夜，301 帧 / 5017 ms | 19.814 ms | 0.761 ms | 0.251 ms | 41.399 ms | 5.234 ms |
| 稳定夜间 | 17.019 ms | 0.589 ms | 0.300 ms | 2.402 ms | 4.570 ms |
| 夜→昼，294 帧 / 4998 ms | 18.676 ms | 0.852 ms | 0.256 ms | 7.714 ms | 8.947 ms |
| 稳定白天 | 19.880 ms | 0.762 ms | 0.162 ms | 4.848 ms | 8.947 ms |

`Process/Physics` 监视器包含整个实战场景，昼→夜样本还包含寻路和调度尖峰，
不能把其差值归因给灯光。灯光自身 CPU 归因应看上面的隔离广播 A/B；实战
样本用于证明实际游戏生命周期和渲染组合没有异常。

## 256 灯真实渲染诊断

该压力场景本身有 8 盏灯，因此夜间总计 264 盏：

| 阶段 | 活跃灯 | Wall p95 | Render CPU p95 | GPU p95 |
|---|---:|---:|---:|---:|
| 初始白天 | 0 | 16.923 ms | 0.562 ms | 0.122 ms |
| 玩家与门夜灯（新增NPC前） | 8 | 16.918 ms | 0.502 ms | 0.271 ms |
| 256 个分散绿环 | 264 | 16.734 ms | 0.590 ms | 0.534 ms |
| 256 个密集绿环 | 264 | 16.739 ms | 0.718 ms | 0.319 ms |
| 夜→昼 5 秒渐变 | 动态 | 16.840 ms | 0.652 ms | 0.900 ms |
| 返回白天 | 0 | 18.614 ms | 0.975 ms | 0.074 ms |
| 昼→夜 5 秒渐变 | 动态 | 16.804 ms | 0.765 ms | 0.205 ms |

压力灯使用 `texture_scale=0.82`、`energy=0.62`。其覆盖面积大于植被环灯的
`0.56/0.40` 和建筑热点灯的 `0.25` 缩放；能量低于当前培育中心的 `0.84`，
但密集重叠面积仍是偏保守的覆盖测试。

夜→昼期间有一次 `109.597 ms` Wall 调度离群值；同帧 Render CPU/GPU
最大值仅为 `1.238/0.980 ms`，Wall p95 仍为 `16.840 ms`，不是持续灯光
卡顿。Wall 时间受 VSync 和系统调度影响，判断灯光开销应优先看 Render
CPU/GPU 与 p95。

一次与用户编辑器并行的快速 GPU 诊断曾测得渐变 GPU p95 `2.001 ms`，
超过探针默认 `1.5 ms` 门槛；同次 CPU 增量仍很低。该结果受两个 Godot
实例争用同一 GPU 影响，不作为 CPU 回退结论，正式 GPU 证书应在关闭其他
GPU 重负载后单独运行。

## 风险分级

- **低：当前稳定状态。** 无逐帧灯光脚本、无灯光阴影、纹理共享，白天关闭
  所有昼夜灯。
- **中但有界：5 秒昼夜渐变。** 每帧为 O(灯数)，512 灯 p95 为
  `1.079 ms`，生产上界 418 灯。
- **低且事件化：建造、拆除、死亡和复活。** 只做常驻灯开关；128 灯批量
  开关 p95 `0.526 ms`。
- **低：科研边框进度。** 仅研发期间按现有 4 Hz 权威事件更新；2×2 占格
  使单机理论上界为 99 个参数写入者，即最多约 396 次写入/秒，无逐帧 Tween。
- **低到中：未来守卫集中死亡。** 活跃灯始终不超过 12，但候选接替通知与
  守卫候选数线性相关。
- **高风险回归条件。** 开启阴影并加入遮挡体、给每盏灯增加 `_process` 或
  Tween、把一张热点纹理拆成多个灯、按距离持续创建销毁灯节点。出现任一
  变化都应重新运行本探针。

## 复现命令

正式渲染样本必须使用真实渲染驱动，不能添加 `--headless`：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648
```

只运行 512 灯广播与生命周期 CPU 基准：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648 `
  -- --cpu-only --micro-samples=500
```

运行 96 个真实敌人的实战昼夜样本：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648 `
  -- --live-gameplay
```

256 灯上限诊断：

```powershell
& 'C:\Program Files\Godot\Godot.exe' `
  --path . `
  --script res://dev_tools/day_night_lighting_performance_probe.gd `
  --resolution 1152x648 `
  -- --lights=256 --warmup=20 --samples=60 --micro-samples=500
```

需要人工检查分散灯布局时，可在 `--` 后追加 `--screenshot`。截图写入
`user://day_night_lighting_probe.png`，不会污染 Git 工作区。

探针内置以下回归门槛：

- 默认 100 灯 Render CPU p95 增量不超过 `0.5 ms`；
- 默认 100 灯 GPU p95 增量不超过 `1.0 ms`；
- 默认 100 灯渐变 Render CPU/GPU p95 增量分别不超过 `1.0/1.5 ms`；
- 超过 100 灯的诊断渐变 Render CPU/GPU p95 增量分别不超过
  `2.0/4.0 ms`；
- 100/256 灯 Wall p95 不超过 `20 ms`；
- 512 灯优化版广播 CPU p95 不超过 `1.25 ms`、max 不超过 `2 ms`；
- 三个 A/B 阶段的优化版总耗时不得比旧版差 5% 以上；
- 禁止发光路径必须比正常变化路径至少便宜 5%；
- 常驻灯关闭/开启必须比完整节点创建、绑定、销毁更便宜；
- 每段默认 5 秒渐变不得早于 `4.8 秒` 完成；
- 返回白天后全部灯关闭，Draw Call 回到初始白天的 ±1。
