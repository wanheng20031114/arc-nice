# 石头人 300 数量压力测试与深因分析

日期：2026-07-18
Godot：4.6.3 stable
渲染：D3D12 / Forward+ / NVIDIA GeForce RTX 3080
测试方式：真实塔防场景与可见渲染窗口，固定种子，60 FPS 上限

> 归档说明（2026-08-26）：对应旧烟测与探针已删除；下方命令和数值仅作为历史记录，后续验证应按当前结构重写。

## 口径

每轮创建 300 个真实石头人，使用生产场景、共享 `GridPathfinder`、
玩家/基地目标分配、身体碰撞、接触 `Area2D`、动画和运行时遥测，不使用空
节点替身。`approach` 覆盖持续移动与寻路；`engagement` 强制附近玩家目标，
覆盖追逐、前摇、砸地和核心接触伤害。

Windows 60 Hz 帧节拍会在 16.667 ms 两侧抖动，因此墙钟主要看 p95/p99，
同时以引擎物理时间、导航积压、热路径累计、节点和内存是否持续增长判断原因。

## 导航频率 A/B

同一未改动夹具分别强制 6 帧和 8 帧刷新，60 帧预热、360 帧采样：

| 指标 | 6 帧（10 Hz） | 8 帧（7.5 Hz） | 变化 |
|---|---:|---:|---:|
| 导航累计 | 1039.550 ms | 866.318 ms | -16.7% |
| 导航/采样帧 | 2.8876 ms | 2.4064 ms | -0.4812 ms |
| 导航刷新 | 15795 | 13230 | -16.2% |
| 导航预算延迟 | 516 | 29 | -94.4% |
| 物理 p95 | 16.885 ms | 15.118 ms | -10.5% |
| 墙钟 p95 | 27.162 ms | 25.623 ms | -5.7% |

300 个单位在 6 帧间隔下平均每个物理相位约提交 50 次刷新。慢帧需要在同一
渲染帧追赶两个物理相位时，约 100 次请求会撞上每渲染帧 64 次的预算，产生
延迟；延迟又会进入后续追赶，放大尾帧。8 帧间隔约为 37.5 次/相位，显著降低
这种反馈。

石头人最终移动速度为 15 px/s，8 帧间只移动约 2 px，远小于 16 px 逻辑格。
直线移动证书会按速度与刷新间隔扩大验证距离，遇障仍回退到 flow field 和
`test_move`，因此只对石头人场景采用 8 帧，不改所有敌人的默认值。

## 最终实现结果

最终实现包含 15 px/s 移速、8 帧导航频率，以及启用的 100 点物理核心接触
伤害。

| 指标 | 300 接近 | 300 持续交战 |
|---|---:|---:|
| 预热 / 采样 | 60 / 360 帧 | 180 / 600 帧 |
| 墙钟 p95 / p99 | 24.984 / 26.907 ms | 25.471 / 28.608 ms |
| 物理 p95 | 12.615 ms | 13.744 ms |
| 导航预算延迟 / 结束积压 | 0 / 0 | 0 / 0 |
| 节点峰值 | 6281 | 6281 |
| 静态内存峰值 | 182.391 MiB | 185.574 MiB |
| 核心伤害调用 | 226 | 5022 |
| 核心伤害累计 | 0.856 ms | 11.930 ms |
| 核心伤害/采样帧 | 0.00238 ms | 0.01988 ms |

交战阶段核心伤害平均每次调用约 2.38 微秒。启用它没有新增节点、Shape 或
`Area2D`：核心区域原本一直参与物理 broadphase，只是骑士继承链把伤害派发
关闭了。本次新增成本仅为发生接触后的冷却更新和每 0.5 秒一次伤害尝试，远低于
导航与通用物理成本。无接触且无冷却时不会进入接触更新热路径，因此不存在阻止
恢复核心伤害的性能问题。

最终交战阶段执行 320 次砸地，纯形状查询累计 8.858 ms，完整处理累计
10.315 ms；分别约为 0.01476 ms/帧和 0.01719 ms/帧。原始 600 帧交战样本也
得到相同量级：328 次完整砸地共 9.971 ms。砸地只占约 17 ms 物理 p95 的
0.1% 量级（平均累计与 p95 不作直接加总），明确不是 300 数量压力的深层
原因。

## 压力的深层原因

300 个石头人同时意味着约 300 个活动 `CharacterBody2D`、300 个持续监视的
接触 `Area2D`、600 个碰撞形状和 300 个动画节点。移动会持续更新 Physics2D
broadphase AABB，并运行状态机、目标有效性检查、导航证书与本地目标索引。
敌人碰撞层不互相碰撞，所以不是 300×300 的敌人互撞，整体仍接近线性，但线性
常数已经足够明显。

既有 Physics2D 隔离测试显示，300 个敌人关闭接触 `Area2D` 可回收约
1.7 ms；这是潜在的大项。但 Area 同时承担玩家/植物进入退出、停步、植物移除
和周期伤害语义，不能为了跑分直接删除。渲染并非首要瓶颈：最终交战的 Render
CPU p95 为 1.302 ms、GPU p95 为 0.450 ms，节点峰值恒定，对象池也没有创建、
丢弃或溢出增量。

## 后续优化优先级

1. 已采用：石头人专属 8 帧导航刷新，保留其他敌人的默认节奏。
2. 高收益但需专项设计：用集中式玩家/植物接触索引替代逐敌人 `Area2D`，逐项
   对照精确进入退出、停步、移除、接触深度和重复伤害语义。
3. 小收益候选：先增加状态分段指标，再合并骑士追逐热路径中重复的目标有效性
   与接触检查，避免盲目影响所有近战敌人。
4. 视觉低优先级：砸地冲击环已有视口预算；可后续让屏外前摇 Polygon 停止逐帧
   写颜色与缩放，但当前渲染数据不支持优先处理它。
5. 不建议削弱砸地精度或截断密集目标查询；Shape、Query、Dictionary、
   Polygon 和 Line2D 已复用，70 个密集植物的分页回归也保证单次只伤害一次。

300 数量仍不能承诺在所有机器上稳定 60 FPS；当前结论是本机最终物理 p95 已
低于 16.667 ms，墙钟尾部仍受 60 Hz 调度影响。正式塔防单波最多 17 只石头人，
其核心伤害派发量远低于压力夹具。

## 复现

```powershell
& .\dev_tools\run_tower_defense_enemy_cohort_probe.ps1 `
  -EnemyConfig res://resources/config/enemies/stone_golem.tres `
  -Phase approach -EnemyCount 300 `
  -WarmupFrames 60 -SampleFrames 360 `
  -NavigationInterval 8 `
  -EnemyHotMetrics $true -RuntimeCountScans $true

& .\dev_tools\run_tower_defense_enemy_cohort_probe.ps1 `
  -EnemyConfig res://resources/config/enemies/stone_golem.tres `
  -Phase engagement -EnemyCount 300 `
  -WarmupFrames 180 -SampleFrames 600 `
  -NavigationInterval 8 `
  -EnemyHotMetrics $true -RuntimeCountScans $true
```
