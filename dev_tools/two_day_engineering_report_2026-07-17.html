01 / Executive summary

这不是一串零散修补，而是一次完整的工程闭环。

两天工作的主线非常清晰：先扩展真实玩法，再由实机 Profiler 暴露规模瓶颈；随后把逐实体、逐节点、逐客户端的重复工作集中化；最后专门审查这些优化，修复冷启动、公平性、生命周期和极端边界。

项目从“每个对象各自解决问题”，转向“共享数据、集中调度、事件驱动、按帧预算、批量绘制与共享编码”。这才是上百乃至上千敌人可扩展的核心。

02 导航从峰值热点变为预算系统

十格玩家追踪、开阔地直追、墙前预取、动态局部流场、Packed 网格快照、generation 原子失效、6:1:1 公平调度共同替代了高频 TileMap 查询与同步全图工作。

03 战斗查询由扫描转为索引

CombatTargetIndex、植物影响格、守护光环覆盖快照把“所有对象扫描”改为局部候选；跨桶事件维护配合每帧 16 项安全审计，控制最坏帧成本。

04 反馈与状态更新由节点转为批次

05 多人 Host 成本不再线性重复编码

协议 v8 先解决恢复、乱序与长期债务，再把等历史客户端合并为共享快照 cohort：每 tick 编码一次、每客户端仍独立发送，基线状态由 C×N 收敛为 N。

06 优化本身接受了逆向审查

最终提交没有继续堆功能，而是回头寻找冷交接、优先级饥饿、到期尾峰、失效绑定和 A/B 开关泄漏；这一步让“快”与“正确”重新合一。

两日形成的统一性能语言

不同系统最后采用了相同的五步模式，这种一致性比任何单点微优化更有长期价值。

Observe先用 Godot Profiler、Visual Profiler 与真实场景定位 inclusive hot path。
Share把逐敌、逐准星、逐客户端重复数据提升为共享快照或共享协调器。
Index把全量扫描改成空间桶、影响格、Packed 快照与积分图证明。
Budget把无法消除的工作切成量子，以渲染帧和微秒预算限制峰值。
Prove保留旧路径做严格 A/B，并用语义签名、压力夹具和生命周期测试闭环。

05 / Navigation reconstruction

把“每只敌人找路”改造成共享、可证明、可预算的导航服务。

这轮重构的触发点不是理论推演，而是实机峰值：某个可见帧达到 137.21ms，其中脚本函数约 63.58–66.71ms，元始虫导航链单帧累计超过 60ms。玩家靠近墙体时，大量敌人停住，则暴露了旧路径在遮挡、证书失效和动态目标交接上的正确性问题。

旧热路径

每个敌人在 physics tick 内从当前位置朝最终目标做长矩形检测；精确 fallback 逐样本、逐候选格反复查询 TileMap 地形/阻挡；失败后再各自建立或请求路径。物理追帧还可能把多个批次挤进一个可见帧。

最终热路径

目标选择限频；开阔地先用 O(1) 快照证书；动态目标只验证当前短 probe；遮挡时复用目标槽位的局部流场。流场扩展和 GridPathfinder 精确 segment fallback 服从渲染帧预算；最终 Physics2D test_move 仍是独立残余成本。

5.1 目标选择：先减少“需要导航”的敌人

GameTowerDefense 只在 0.60 秒重选周期到期时安排目标查询，并把每个 physics frame 的重选上限设为 16。决策顺序是：8 格内可攻击植物 → 10 格内玩家 → 固定核心/蓝门目标。这里的“10 格”是玩家成为候选的索敌半径，不是局部动态流场的尺寸；选中玩家后，直接追踪/动态流场的工作半径仍可到 16 格。

这同时修复“追踪几秒前位置”的根因之一：目标身份可以低频选择，但选中玩家的目标坐标必须来自当前帧，不能把上一次重选时的位置当成永久终点。目标槽位会在目标移动 2 格或年龄达到 0.25 秒时刷新，同时保留上一张字段约 1 秒，避免更新期间整群停摆。

5.2 数据平面：把 TileMap 从稳态热路径移走

GridPathfinder.rebuild() 生成两套只读快照。基础 PackedByteArray 的最高位表示阻挡，低位表示地形穿越类型；agent profile 则生成实体净空字节、每格 8 方向合法移动/防对角穿角掩码与 PackedInt32Array summed-area table。直线短步的扫掠矩形如果在积分图中为零，即可 O(1) 证明整个区域无 agent-solid 单元。

精确 fallback 也不再盲目访问 5×5 候选：对每个采样点先计算 agent 几何体与格子 AABB 是否可能相交；不可能接触的格子直接跳过，只对几何上确实可能相交的少数候选读取阻挡/地形快照。这样保留原来的精确碰撞语义，却切掉大量函数调用和多层 Dictionary/TileMap 查询。

地形变化的原子性

已接线的 LAND↔WATER terrain_changed 会先立即递增 generation、把 is_built 置假并取消旧 job/slot；随后用 call_deferred 合并变化，并在后续主循环同步扫描 used region、重建基础快照。旧地形证书从变化同帧起失效。Obstacle TileMap 变化则必须显式调用 rebuild；运行时植物/建筑不在这张 raw snapshot 中。

5.3 控制平面：共享流场、优先队列与公平预算

动态目标字段不是“每只敌人一张 A*”。DynamicFlowTargetSlot 以目标、agent profile、地形穿越能力和接触规则为键；同组敌人的 source cells 合并到同一个 runtime job。字段使用 16 格半径的局部区域、packed region index 和 15 桶 Dial queue，直移权重 10、斜移权重 14。相同帧的 prefetch 还按目标/profile/2px 位置桶去重，避免一群重叠敌人重复提交同一请求。

流场 job 构建发生在 render-frame 的 _process，而不是 physics frame。每次最多推进约 192 个扩展并受 1,000µs 软预算约束；GridPathfinder 的精确网格 segment fallback 另有每渲染帧最多 32 次/750µs 的总闸门。Enemy 最终调用的 Physics2D test_move 只做错峰/缓存，并不计入这 32 次/750µs。调度循环按 D,D,D,S,D,D,D,B（动态、静态、后台）运行，形成约 6:1:1 的服务比例；每个 job 的量子为 8，优先 band 内轮转。

冷交接

新字段构建时旧字段仍可读；新场原子发布，旧场最多保留约 1 秒。没有可用字段时使用短步证书/保守 fallback，而不是输出持续零方向。

墙前预取

开阔地直追期间每 6 个 physics frame 看前方约 3 格；遇到墙之前就把 source 加入字段，避免碰墙后才从零启动。

长距与贴身修正

长距离 stale-anchor direct correction 要求完整 corridor 证书，不能因局部 probe 安全就穿越远处障碍；进入 contact radius + margin 后的 final alignment 则使用短积分证书并再经真实 shape test_move。

动态物体边界

raw snapshot 只读取 terrain traversal 与 obstacle TileMap 的 TileData collision。植物/建筑占格没有接入 generation，而由 Physics2D/接触攻击处理；移动实体同样不在静态证书中。

5.4 “平地无脑直追”为什么没有做成一张永久标签图

用户提出的“开局预标注超大平地”方向是对的，但最终实现选择了更一般的积分图证书：它仍然让开阔区域 O(1) 命中，又能为不同 agent 尺寸和地形能力分别构建净空规则。当前只有地形切换接入 generation 自动失效；新建筑由 Physics2D 检查，不会事件驱动更新这张快照。若以后要把植物纳入证书，应先设计局部增量或显式 rebuild，不能把它当成已完成功能。

固定核心/蓝门适合地图级流场；玩家则是短寿命动态目标，使用局部目标槽位更节省构建量。两者组合比“所有目标都做全局流场”更适配当前地图：大平地占比高时，大多数敌人保持直追；只有被墙、植物或地形转折遮挡的一小部分进入共享局部场。

仍然存在的最坏情况

1,000µs 是脚本层软预算，不是硬实时中断：一次原生调用或一次 16 项 batch 仍可能跨过预算；Physics2D test_move 更不属于该预算。基础 raw snapshot 的 deferred 重建仍会一次同步扫描 used region，复杂障碍覆盖也可能让证书进入精确队列。系统显著缩短稳态热路径，但不应描述成“任何地图都绝无尖峰”。

6.3 最终审查为何重要

第一次优化通常压低平均成本；最终审查专门寻找最坏帧。它修复了导航调度器每次重新扫描 job、冷场交接期间 direction 归零、短尾 job 不检查时间、准星 coordinator 失效绑定双路径、对象索引跨桶安全审计，以及 A/B 开关意外改变正式行为。这些问题若只看平均值很容易漏掉，恰好却会表现成玩家感知最强的“偶尔卡一下”。

如何在 Godot 中复核 CPU，而不是只看 FPS？

编辑器运行游戏后打开底部 调试器 → 分析器，测量选择“帧时间（毫秒）”，同时勾选 Frame Time、Physics Frame Time、Script Functions 和 Physics 2D。遇到尖峰时停止采样，按“时间”排序并向下展开 inclusive 调用链；再在 可视分析器 中区分 Render CanvasItems、Render Viewports 与 GPUParticles。最小化后帧耗时明显下降，说明可见 Canvas/viewport 绘制占比真实存在，但不能据此排除脚本热点，因为窗口最小化会改变渲染节奏和调度。

当前主线没有接入 F3 调试面板。仓库存在 runtime_performance_telemetry.gd 与开发测试，但没有 KEY_F3、输入 action 或游戏内 overlay wiring；报告不会把设计意图写成已完成功能。

07 / Final architecture

最终形态：权威逻辑立即完成，昂贵表现与重复计算延后、共享或批量。

导航、多人快照、建筑生命周期、状态效果与视觉反馈看似无关，实际都遵循同一个边界：玩法状态必须确定且可恢复；表现和计算可以预算，但不能反过来拖住权威状态。

7.1 五条跨系统架构原则

A单一权威数据源

Host 决定玩家复活、敌人奖励、植物撤除和快照 revision；客户端只消费可靠事件或容忍乱序的 snapshot，不通过本地视觉推断游戏状态。

B明确数据所有权

Grid/flow snapshot 构建完整后原子发布；Guardian 在单个 physics 调用内重建并消费可变 coverage 工作集；Host encoder 单线程维护 cohort baseline。三者都避免跨 owner 读半状态，但实现模型并不相同。

C事件维护、查询变便宜

植物放置/撤除、敌人跨桶、静态小地图变化和地形 mutation 承担更新成本；每帧查询只读预计算结构。

D明确过载语义

导航与慢速到期把超额工作保留为 pending；伤害数字超预算会省略视觉；快照发送 tick 仍遍历所有 chunk×peer，并没有微秒级 pending 队列。每个系统的取舍必须分别说明。

E语义 fallback 可解释

证书失败进入精确检查；快照历史不一致发送 full；对象池满则省略粒子；没有任何 fallback 会悄悄伪造死亡、奖励或碰撞结果。

7.2 多人快照共享：省编码，不放宽一致性

任何成员变化、identity 不一致、缺历史、恢复、或 0.5 秒 full 周期都会让整个 ready set 发送完整状态。空 cohort 立即释放 baseline。客户端继续使用 sequence/revision/tombstone 拒绝旧生命包与迟到敌人状态；因此这次优化没有新增协议字段，也没有放宽一致性。56 只限制单个敌人包的 chunk 大小，发送 tick 仍需逐 peer 发出全部 chunk。

7.4 奖励、生产与流程的一致性

息壤奖励

敌人死亡不再生成息壤小球、manager 或碰撞对象。死亡只提交配置的结晶奖金；GameRuntimeBase 同帧聚合、deferred flush 给当时所有在线玩家。协议 v8 的旧 RPC shell 仍保留空实现以兼容消息表。

其他掉落

3% 材料掉落仍存在，报告不把“删除息壤小球”误写成“删除所有拾取物”。玩家在死亡与 deferred flush 之间加入/离开时，以 flush 时的 peer 集合为准。

仓库生产

09 / Boundaries & decisions

已知边界不是失败记录，而是下一轮优化的导航图。

最终版本已具备很强的可用性；下一步应优先处理能造成可见尖峰或一致性风险的边界，而不是继续扩大抽象层。

导航软预算仍可过冲

原生调用和 batch 不能被 GDScript 中途打断。建议在真实 300/600/1,000 敌人场景记录每类 job 的 p50/p95/p99、超预算次数与单次最大 native call；只有证据指向 Physics2D 时再扩展证书。

动态流场复杂覆盖

复杂转角、窄门或 agent profile 覆盖不完整时会进入 DEFERRED/精确 fallback。下一轮应增加按地图区域的“证书失败热力图”，而不是假定所有平地都命中。

CombatTargetIndex 极端跨桶

所有敌人每帧跨 96px 桶时，A/B 的 old/new speedup 只有 0.69–0.82×；等价地，新事件路径耗时约为 legacy 的 1.22–1.45 倍。现实场景通常不会持续发生，但高速冲刺/传送波次应单独监控。

共享快照 full spike

新加入、恢复或 cohort 成员变化可能让整组在同 tick 发送 full。CPU 编码仍共享，但网络带宽会尖峰；应记录 full reason、cohort size 与发送字节，而不是仅看编码耗时。

到期语义尾差

本次 1,000 目标/单 source 复测用了 10 个渲染帧；2,064 work units 夹具用了 17 帧，更大或多来源 backlog 还会更久。若未来要求严格同帧解除，应把 modifier 的“逻辑有效期”与“清理回调”分离，而不是简单提高每帧上限。

基础快照仍同步重建

地形变化虽然 deferred 合并，但下一主循环仍一次扫描 used region；建筑/植物也未进入 raw snapshot，只能由 Physics2D 处理。后续应先量化重建尖峰与动态障碍命中率，再决定局部增量方案。

奖励 flush 成员边界

敌人死亡与 deferred flush 之间发生加入/离开时，以 flush 时在线玩家为准。若设计期望“死亡瞬间在场者”，应在提交奖励时冻结 peer 集合。

小地图与 Canvas 成为下一热点

最小化后明显变快，加上后续 Profiler 中 minimap draw 约 3.86ms，说明渲染提交仍值得关注。优先比较可视/隐藏小地图的同场景 A/B，并检查 viewport/CanvasItem 数，而非先改 GPU shader。

缺少游戏内性能面板

F3 overlay 尚未实现。建议只读展示 frame p95/p99、脚本/物理/Canvas、导航 job/pending/overshoot、索引跨桶、快照 cohort/full reason；默认 release 不启用，避免重新引入已撤销的调试权限范围。

9.1 建议的下一轮顺序

P0 · 可观测性

先落地只读性能采样层和可导出的滚动统计；F3 只负责展示。没有 p95/p99 和事件计数，继续优化容易重新回到凭截图猜测。

P0 · 真机导航矩阵

固定地图、固定 seed、固定 300/600/1,000 敌人，分别测试开阔地、单墙、窄门、玩家贴墙、建筑频繁放置；记录证书命中率、fallback、field publish 和零方向持续帧。

P1 · Canvas 隔离

四组 A/B：小地图 visible/hidden、damage feedback on/off、生命周期粒子 on/off、敌人 sprite 可见/不可见；用相同模拟 tick 判断最小化收益究竟来自哪一层。

P1 · 网络尖峰

模拟 7+ 客户端同时恢复、ready-set 成员变化与 0.5s full 周期重合；门禁从平均 encode time 扩展到最大 tick bytes 和 full reason 分布。

P2 · 语义收口

文档统一采用“施工完成后 1.50s / 放置后总计约 2.20s”的粒子口径；再依据玩法决定奖励 peer 冻结时点与 slow tail 语义。这些是产品决策，不宜由性能 fallback 默默决定。

最终判断

这两天最重要的成果不是某个 43× 数字，而是项目已经具备“热点出现 → 建立可复现夹具 → 共享/索引/预算 → 逆向审查 → 留下边界”的优化循环。只要下一轮继续坚持相同证据纪律，大规模敌人并不是不可控目标。
