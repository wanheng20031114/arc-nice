# 新敌人制作 Pipeline

把新敌人视为一个需要逐门批准、可复现构建和分层验收的产品功能，而不是一张图加一个场景。先读项目根目录的 `AGENTS.md`，再按本流程推进。

## 硬门禁

1. 视觉发生变化且没有可复用的既有批准素材时，最终视觉批准前只写开发素材和构建工具，不写对应运行素材与视觉接入。纯玩法变更、已批准素材复用或用户明确要求跳过视觉门时，记录依据后按实际影响推进。
2. 审美选择由人工确认；尺寸、哈希、碰撞、权威性和计数等不变量由自动审计证明。两者不能互相替代。
3. 同一文件或产物目录只允许一个写入者。并行任务必须有互斥边界，共享注册表和协议由整合者统一落盘。
4. 默认朝向、视觉前方、攻击跟踪、锁向时刻、预警形状和伤害查询必须使用同一方向语义。
5. Host 权威、受影响能力的回归测试和验证进程清理都属于交付内容；只有用户授权 Git 同步时，远端一致性才属于本次交付内容。
6. 像素敌人的主视觉原稿必须从一开始就是目标像素语言。高细节概念图、平滑渲染或强 3D 稿不能作为原生像素锚点，也不能靠点表主观“翻译”为另一套造型。
7. 原稿必须在所选运行表示的实际预览中直接读清轮廓、肢体、握点和附件关系。原生分支检查 native 1:1 与整数倍最近邻预览；高分辨率原图保真分支检查原图 1:1 与声明的运行缩放/线性过滤预览。做不到就重生原稿，不进入重建、动画或运行时阶段。
8. 物理分辨率与逻辑像素量必须分开审计。本条只判定 native 候选：像素稿只有两种来源可以产出 native 候选——ImageGen 直接输出最终 native 尺寸；或所有帧都证明为同一逻辑画布按同一个整数倍率、同一个格距和同一个格相位展示，并逐格一对一还原。不得用固定比例适配、整格投票、逐帧相位、特征保真评分、拓扑相似或肉眼观感替代这项证明。任何 resize、downsample 或 many-to-one 结果只能用于诊断，不能进入像素 native 候选。证明失败时，默认只把 SHA 锁定的已批准主视觉锚点作为 ImageGen 图像输入，并用文字重新声明本套动作；不得把失败动作稿递归传入。新输出重新进入人工门，旧批准不得自动转移。只有用户明确批准“高分辨率原图保真运行时”时，才能改走独立的非 native 分支；该分支永远不得标记为 `native`、`native64` 或数学原生。
9. 高分辨率原图保真分支的 ImageGen 源图必须原生带透明背景，素材构建禁止空间重采样。只允许透明裁切、整数像素平移、透明补边和无损打包；所有帧必须进入共享虚拟画布并使用同一注册点/脚底基线。所有可见像素的 RGBA 必须逐像素守恒，透明像素 RGB 必须清零；任何裁切、漏像素、软 alpha、颜色漂移或帧间独立缩放都必须 fail closed。缩放只在运行时以统一 transform 执行，并显式声明过滤方式；用户批准时允许线性过滤，但不得把过滤结果烘焙回运行纹理。

## 先选择任务分支

不要把同一套具体参数套给所有敌人。先判断：

- **全新敌人**：需要同时定义身份、轮廓、玩法、分类、掉落和投放范围。
- **派生或精英敌人**：先冻结原版必须继承的不变量，再列出允许变化的差异预算。
- **低分辨率像素素材**：优先让 ImageGen 直接生成带原生透明背景的最终 native 尺寸，或生成可证明为统一整数倍展示的低逻辑分辨率、有限调色板、硬边方形像素候选。确定性步骤只能按已证明的整数格逐格一对一还原、整数像素裁切/补边和有限可审计清理，不得通过空间重采样重新发明轮廓、姿势或持物关系。
- **高分辨率原图保真运行时**：只有用户明确批准直接使用高分辨率原图时启用。将 SHA 锁定、原生带透明背景的批准原图作为 canonical source，只做透明裁切、整数平移、透明补边和无损 atlas 打包；不 resize、不 downsample、不重画。所有帧共享虚拟画布、注册点和脚底基线，运行时只用统一 scale；显式记录并验证线性或项目批准的过滤方式。该分支是非 native 表示，永远不得称为 `native64`。
- **纯接触敌人、主动攻击敌人、投射物敌人或持续状态敌人**：按实际能力选择最小运行时与联机表面，不强行补齐不需要的系统。

帧尺寸、帧数、FPS、属性、动画名、人审门数量和协议版本都是每次任务的参数，不是本 Pipeline 的常量。

## 阶段 0：核对基线与文件边界

1. 检查分支、工作树、已知远端基线和已有用户修改；只有任务需要且用户已授权同步时才 fetch。
2. 找到最接近的敌人族、行为基类、场景结构、配置资源、图鉴条目、掉落表和测试。
3. 记录当前图鉴、纹理、派生映射、模式与协议计数；不要凭记忆填写。
4. 为并行工作划分文件所有权。共享文件只交给一个整合者。
5. 形成计划，明确哪些阶段需要用户确认，哪些分析可以并行。

## 阶段 1：冻结敌人契约

在生图或写代码前，用简短清单确认：

- 身份、体量、轮廓、配色、材质、携带物和禁止元素；
- 移动、攻击、受击、死亡及可选特效；
- 属性、奖励、分类、掉落与允许出现的模式；
- 身体碰撞、接触伤害区、主动攻击范围、视觉武器和世界碰撞之间的关系；
- 攻击何时跟踪、何时锁向、何时结算，以及目标绕后或离开范围时的语义；
- 特殊承伤或状态规则在结算链中的位置，以及标量、批量、DoT、无效、致死和死亡后请求的行为；
- Host 与代理端职责；
- 与现有出生、受击、死亡和状态反馈是否重叠或冲突；
- 明确非目标，例如不新增投射物、RPC、频道、快照位、对象池或材质副本。

不确定项应先给少量真正不同的方案让用户选择；不要用宽泛 fallback 同时实现多种互斥语义。

## 阶段 2：通过视觉确认门

视觉发生变化时默认采用以下门。复用既有批准素材或纯玩法任务可记录来源后跳过；简单任务可经用户同意合并，复杂特效可增加独立门。

### 主视觉锚点门

- 为真正不同的轮廓、比例或持物关系分别生成参考。
- 目标是像素素材时，每案原稿本身就必须是像素画，并先声明运行表示。原生分支声明最终 native 尺寸、逻辑画布、有限视觉色阶、禁止抗锯齿/渐变/平滑笔触，并同时展示 native 1:1 与整数倍最近邻视图。高分辨率原图保真分支声明源尺寸、共享虚拟画布、统一运行 scale 与过滤方式，并同时展示原图 1:1 和实际运行缩放预览；线性过滤只允许用于该预览和运行采样，不能产生新的纹理文件。ImageGen 文件中的同色微小 RGB 漂移可以量化，但不能通过软化或重采样掩盖。
- 原生分支在生成前声明最终 native 画布、主体最大逻辑 bbox，以及“直接 native”或“统一整数倍展示”之一；动画所有帧共享同一逻辑画布、格距、格相位和主体尺度。若原稿虽“看起来像像素画”但无法给出正向整数格证据，默认只携带已批准主视觉锚点回到 ImageGen，用文字逐帧重生该动作；不要把失败动作稿、压缩稿或适配结果当成新输入。只有用户明确改选高分辨率原图保真分支时，才改为声明源尺寸、共享虚拟画布、整数帧偏移、统一运行 scale/filter 和 `native_eligible=false`。
- 优先把项目内已批准的原生精灵作为调色板、像素密度和设计语言参考；不要把高细节概念渲染当作像素源。
- 每案单独保存原稿、提示词和来源哈希。
- 展示原稿、运行候选、左右朝向、轮廓/注册点/碰撞叠加和尺寸对照。原生分支只用 native 或严格整数倍最近邻视图；高分辨率原图保真分支可额外使用声明的统一运行 scale 与线性过滤预览，但必须标注 `highres_source_preserved`、源尺寸、scale 和 filter，且不能把预览缩放结果写成候选纹理。
- 原稿与所选运行候选必须保留同一可辨轮廓、姿势、手脚和附件布局。若需要靠主观重画才能成立，判定原稿失败并重新生成。
- 多武器角色要分别声明每只手、握点、武器所在身体侧和允许的遮挡；逐件验证“手 → 握柄 → 武器”连接，不能只验证武器数量或整体连通。
- 批准后冻结核心轮廓、注册点、默认朝向、握点和附件尺寸。

### 动画门

- 按移动、攻击、死亡和必要状态分别提供方案。
- 每套动作必须以已批准主视觉锚点作为实际 ImageGen 图像输入，分别发起独立生成。默认只传主视觉锚点，不把旧动画 sheet、压缩稿、native 尝试或另一套动作作为输入；只有用户明确批准追加动作参考时才允许多图输入，并逐项记录其 SHA。禁止用前一套动画递归生成下一套，避免身份、像素密度和轮廓逐代漂移。
- 一个动作跨两个 sheet（例如前摇/冲锋与圆斩、起跳与落砸）时，每个 sheet 仍是一次独立 ImageGen 调用，但必须锁同一主视觉 SHA、角色身份合同、镜头尺度和帧语义。新生成的 raw 先回到动画人工门；不得先压缩、下采样、点表重画或 native 化后才展示。
- 每案提供独立正反向 GIF、逐帧差分和稳定报告，不用一张大拼图替代动作检查。原生分支 GIF 只使用 native 或严格整数倍最近邻帧；高分辨率原图保真分支允许使用声明的运行 scale 与线性过滤制作审阅 GIF，同时必须保留原图 1:1 逐帧证据，并证明 GIF 缩放未进入 canonical/runtime 纹理。
- 明确帧数、运行 FPS、循环方式、切换相位和伤害帧。GIF 延时只用于审阅，不得反推运行 FPS。

### 可选表现门

仅在尾影、护盾、召唤物、弹体或复杂特效需要独立判断时增加。检查共享材质、状态染色、方向切换、清理时机和性能边界。

### 最终运行候选门

- 拼装最终 atlas 或独立帧资源。
- 展示所有动作、动作串联、左右镜像、阶段切换、碰撞/攻击叠加和世界尺寸对照。原生分支全部使用 native 或严格整数倍最近邻展示；高分辨率原图保真分支同时提供原图 1:1 证据与标注 scale/filter 的运行尺度线性预览。
- 审计素材与已批准方案逐帧一致。
- 用户明确批准后，才允许进入运行时发布。

每一门都必须记录 `pending/approved` 状态、选择项和证据。不要从语气或旧消息猜测批准。

## 阶段 3：构建可复现素材

对于本项目的低分辨率像素敌人，默认执行：

1. 先生成像素原稿：目标逻辑分辨率、硬方形像素、有限视觉色阶、无抗锯齿、无渐变、无高细节 3D；在目标 1:1 下审查，而不是只看大图。
2. 原稿先通过轮廓、姿势、肢体、握点、附件位置和像素密度门。原稿失败时立即重生，禁止用后处理掩盖。
   网格归一前记录原稿物理尺寸、最终 native 尺寸、统一整数展示倍率、全帧共用的格距/相位、主体逻辑 bbox、可见逻辑格数和 source→native 单射。直接 native 分支必须证明没有空间重采样；整数展示分支必须证明每个逻辑像素恰好对应同尺寸的整数方块，且所有帧使用同一倍率和相位。不同帧分别拟合比例或相位、整格投票、边缘拟合、特征评分与拓扑检查都只能诊断，不能通过本门。
3. 从通过的像素原稿确定性获得原生帧。ImageGen 输出必须原生带透明 Alpha；缺少透明通道时直接返回生图门，不得由代码根据 RGB 推断前景。直接 native 分支只允许整数像素透明裁切/补边和明确列出的少量颜色清理；整数展示分支只允许把已经证明完全一致的整数展示块逐格解码为一个 native 像素。禁止调用 resize/downsample 生成 native，禁止用中心采样、覆盖率、多数票或加权票决定混合格。
   可见主体同色区域的微小 RGB 噪声只能在空间格证明通过后映射到预先冻结的固定调色板；每个整数展示块在映射后必须只有一个 Alpha 状态和一个颜色，mixed-cell 直接失败。这类编码漂移不能被误报为原稿已经数学原生。
   Alpha 判定与描边颜色必须分开：不得为了“补黑边”降低实体阈值、投票补实体、膨胀轮廓或堵住负空间。只能对已有 Alpha 边界按可追溯颜色证据规范化，并分别报告外轮廓边界与封闭负空间边界。
   左右功能色或成对装饰不得盲镜像。自动规则只能统计并在不满足时阻断人审；人审批准的少量改色必须是 Alpha 不变、SHA 锁定、before/after 明确且由通用数据合同驱动。
4. 显式蒙版、点表或逐帧规则可以用于修边和动画，但不得改变已批准原稿的语义结构。若必须重画头身比例、肢体、武器侧别或姿势，返回生图门。
5. 用 `dev_tools/pixel_crop_tool.py`、`dev_tools/pixel_grid_analyzer.py` 或本 skill 的分析脚本测量，禁止任何非整数展示缩放、native 空间重采样、软化 alpha 或凭视觉猜逻辑网格。诊断工具给出的候选尺度、逐帧相位或“看似保真”结论不得充当发布证书。
6. 为每个任务自行声明帧尺寸、中心、脚底基线、安全边距、最大可见范围、禁止区域、连通性和附件连接合同。
7. 审计二值 alpha、透明像素 RGB、调色板、主体漂移、串帧、附件连接、动作相位、镜像，以及原稿语义保真度。对头/眼、手/握点、脚、武器端点等关键地标，必须在原稿、逻辑格规范化结果和 native 1:1 中逐项核对；轮廓连通或整图相似度不能代替地标保真。整体连通也不能代替轮廓完整性：检查外轮廓、封闭负空间边界、非声明凹口/尖刺和断续描边。
8. 连续构建两次；输入未变时，文件哈希和解码像素哈希必须零漂移。

以上 1–8 是低分辨率 native 分支。用户明确批准高分辨率原图保真运行时时，改执行以下独立构建合同，不得把两套证据混写：

1. 锁定每张原生带透明背景的已批准源图的文件 SHA、解码像素 SHA 和帧语义；未批准帧不得进入运行 atlas。
2. 从源图到运行纹理只允许透明 bbox 裁切、整数像素平移、透明补边和无损打包。禁止 resize、downsample、旋转、非整数平移、重绘、形态学补边、羽化与颜色量化。
3. 为所有动作声明同一个 `virtual_frame_size`、中心、脚底基线和注册点。每帧只能以整数偏移放入共享虚拟画布；溢出、触边或需要逐帧 scale 时立即失败。
4. 对每帧记录源、虚拟画布和打包后的可见像素数及可见像素 RGBA 哈希。可见像素的 Alpha 与 RGB 必须逐像素守恒；透明像素 RGB 清零。
5. Atlas 裁切仅移除透明区，并用 `AtlasTexture.margin` 恢复统一虚拟画布；所有 `region` 必须在 atlas 内并启用 `filter_clip`。任何可见像素被裁掉都 fail closed。
6. 运行时只允许在 `AnimatedSprite2D` 上设置一个全帧共用的正数 uniform scale；朝向使用镜像，不得按动作或帧缩放。显式记录 `texture_filter`；用户已批准时可用线性过滤，并以足够透明 guard 防止 atlas 串色。过滤只发生在采样时，不生成缩放后的运行纹理。
7. 审阅同时保留原图 1:1 逐帧证据和实际运行 scale/filter 的预览。此分支报告 `runtime_representation=highres_source_preserved`、`native_eligible=false`，禁止出现 `native64=true` 或等价声明。
8. 连续构建两次并比较 atlas、`SpriteFrames`、逐帧逻辑尺寸、margin、像素守恒报告与文件哈希，任何漂移都停止发布。

需要处理粗网格、主体锚点、`AtlasTexture.margin` 或中心公式时，读取 [精灵素材技术参考](references/enemy-sprite-pipeline.md)。

## 阶段 4：建立证书链

把 preview builder 与 runtime writer 分开。

- Preview builder 只能写开发目录，并限制输出白名单。
- Canonical manifest 必须声明唯一证书所有者。Preview builder 和 runtime writer 只输出各自阶段的报告，由该所有者顺序更新批准状态；禁止多个工具并发改同一证书。
- Manifest 记录阶段、批准项、输入/输出路径、文件 SHA、解码像素 SHA、运行时是否已写入和写入路径。
- Report 记录审计事实，不承担批准语义。
- Stability 记录至少两轮确定性快照及漂移数。
- 缺文件、输入漂移、阶段混用、批准项不一致或提前声称发布时必须 fail closed。

文件 SHA 证明字节一致；解码像素 SHA 证明视觉数据一致。不要把两者混成一个证据。

## 阶段 5：显式发布运行资源

最终批准后使用独立 writer：

1. 要求显式发布参数；无参数调用应拒绝写入。
2. 验证最终批准证书、输入哈希、目标白名单和运行路径。
3. 按已批准的运行表示发布纹理，并确定性生成 `SpriteFrames` / `AtlasTexture`；高分辨率原图保真分支不得生成任何缩放后的中间或运行纹理。
4. 保留或正确生成项目 UID、导入设置、动画名和 `filter_clip`。高分辨率原图保真分支还要写入统一 scale、声明的过滤方式和透明 guard 合同。
5. 连续运行两次验证幂等。
6. 把每个最终运行路径的文件哈希和适用的解码哈希交给证书所有者回写。

Writer 只发布素材，不应偷偷修改玩法或绕过人审。

## 阶段 6：实现最小运行时

1. 优先复用最接近的行为族、配置和 Godot 原生节点。
2. 新增节点类型或不确定场景结构前，先查 Godot 官方文档，再选择原生节点和资源方案。
3. 共享基类需要扩展时，使用默认关闭的配置或小型虚方法，保证其他敌人不变。
4. 场景节点优先静态写入 `.tscn`；避免运行时动态拼装本可在编辑器表达的结构。
5. 明确分离身体世界碰撞、接触伤害区、主动攻击查询、预警和纯视觉附件；持续状态切换还要冻结各节点启停顺序。
6. 攻击查询只在明确伤害时刻执行，并按目标实体去重。
7. Host 唯一执行伤害、状态触发、掉落、死亡和权威移动；代理端只补播表现。
8. 优先复用既有动作同步、快照和乱序保护。现有表面足够时，不新增 RPC、频道、状态位或攻击 ID。

共享结算、掉落或状态接口的默认路径必须有原型回归测试。

## 阶段 7：按影响面完成集成

- **分类与掉落**：分类标签只表达分类；特殊掉落使用显式表。继承表要验证基础优先、单次展开、重复引用和循环安全。
- **图鉴与资源计数**：更新条目、排序、分类、阶级、纹理和派生映射计数。
- **模式与波次**：使用白名单思维声明允许投放的位置；对其余正式、测试或肉鸽内容增加零直引保护。
- **加载与预热**：只有实际需要固定预热、池化或高频资源时才加入对应清单。
- **联机与协议**：出现新 wire key、网络字段或资源合同后，先读取最新远端基线，再分配下一协议版本；原子更新主项目、Relay、`relay_servers/README.md` 和断言。
- **兼容边界**：没有新增协议表面时，明确验证 RPC、频道、快照位和注册 ID 未变化。

## 阶段 8：分层验证

按风险由窄到宽执行，只启用实际受影响的层级。小改动遵循 `AGENTS.md` 的轻量验证规则，不强制运行无关宽测试：

1. 素材：尺寸、帧组、FPS、循环、alpha、调色板、锚点、安全区、连通、镜像、切换与导入设置；高分辨率原图保真分支额外验证无空间重采样、逐帧 RGBA 守恒、共享虚拟画布、uniform scale、声明的线性过滤、透明 guard 和 `native_eligible=false`。
2. 行为：属性、冷却、伤害时序、特殊结算、批量/DoT/无效/致死边界。
3. 碰撞：身体、接触、攻击范围、墙体、水域、导航、多形状去重和视觉附件不参与物理。
4. 联机（联机行为或网络可见资源受影响时）：Host 唯一伤害、代理零伤害、重复/乱序/迟到、持久状态中途加入恢复和死亡清理。
5. 集成：图鉴、掉落、模式、波次、派生映射、加载、协议和零直引。
6. 回归：被复用的普通敌人和共享结算/掉落/同步能力。
7. 资源变化时运行 Godot 导入；运行聚焦无头测试和 `git diff --check`；只有协议、RPC 或 Relay 受影响时才运行 Relay 测试。

把已有但与本次无关的基线失败和本次引入的失败分开报告，不要用旧失败掩盖新问题。

用户否决某一视觉门时，立即把该门及其下游证书标记为失效；被否决的原稿、点表和候选不得继续作为新方案的视觉输入，只能保留为失败记录。

详细契约模板、证书字段、测试矩阵和失败模式见 [端到端集成检查表](references/new-enemy-integration-checklist.md)。

## 阶段 9：同步与交付

1. 只有用户明确要求同步远端、提交或推送时，才执行对应 Git 操作；普通实现请求不自动获得这些权限。
2. 需要同步时先保护现有用户改动，再 fetch/rebase 最新远端并重新确认计数与协议版本。
3. Rebase 前保留可恢复备份；解决冲突时同时保留远端新语义和本任务语义。
4. 冲突后搜索冲突标记、旧“当前版本”断言、重复注册和失效资源路径，并重跑受影响测试。
5. 除非用户明确要求保留，只停止本次启动的验证进程。按命令行识别无头 Godot、测试 Python、Relay 或辅助服务器，绝不关闭普通 Godot 编辑器。
6. 清理后再次核实并报告所有本任务辅助进程的残留数量。
7. 若执行了提交和推送，再确认工作区状态及本地 HEAD 与目标远端的一致性。
