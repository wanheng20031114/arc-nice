# 塔防大规模战斗结构审计（2026-09-08）

## 范围与基线

目标是大量建筑、300 个敌人、6 人联机时的持续卡顿和结算尖峰。已先快进拉取远程 `ee0c9a1c3230`，并继续整合任务期间新增的 `38a8742dd28d`（小车十二波战役、敌人血条）。测试引擎为本机 Godot 4.6.2 stable，测试脚本与结果口径分别记录，不能把无窗口 CPU 结果当作实机 GPU 帧率。

采用 Godot 原生节点、资源、信号、性能监视器与微秒计时，遵循[官方 CPU 优化指南](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)要求的测量和对照。

## 阶段一：生产仓库的乘法开销

### 根因

`ProductionCoordinator._on_warehouse_storage_changed()` 原先会在任何仓库变化时失效整张库存聚合表。紧随其后的每次配方预检、产物容量检查或 UI 读取都重新扫描所有可用仓库的全部槽位。多个生产建筑在同一个一秒 tick 完成时，代价随「完成次数 × 仓库数 × 每仓槽位数」增长。

另外，公共通知之前的无信号原子写入不会失效旧聚合缓存。已预热的缓存可能在下一笔无信号事务读取时返回旧总数；原版回归可复现失败。

### 实现

- 每个仓库保留独立的物品数、现有堆叠剩余空间和空槽贡献；只有提交过变更的仓库被重新读取并替换其聚合贡献。
- 仓库修订号提交时直接标记所属聚合缓存脏，无信号提交和回滚都覆盖。失效方法只标记数据，不发信号、不执行事务。
- 建造完成、移除、重新注册等成员变化仍完整重建排序与聚合，保留确定性的消费顺序。
- 客户端仓库计入可见总量，但不能参与权威生产原料与容量预检。
- 隐藏的简易制造页不响应每次生产事件重复重建图标和文本；可见页面把同帧事件合并到一次刷新，重新显示时读取最新状态。
- 生产产物气泡在配方、显示状态和工作状态都未改变时跳过重复主题、图标和尺寸设置。

### 回归与测量

入口：`dev_tools/production_storage_scaling_regression.gd`。

```powershell
Godot_console.exe --headless --path . --script res://dev_tools/production_storage_scaling_regression.gd
```

128 个真实橡木仓库，6 组各 100 次环境来源生产提交，每次立即检查累计数量：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 100 次提交耗时，预热后 | 35.47–35.57 ms | 7.22–7.46 ms |
| 600 次单仓提交重扫仓库数 | 76,800（按原路径推导） | 600（计数器实测） |
| 无信号提交后的缓存读取 | 回归失败 | 通过 |

修改后的回归还检查：每次实际产出数量、移除/重注册、无信号提交、回滚、多仓批量快照首个公共通知即观察完整提交、建造中仓库排除、完工后纳入、客户端可见库存与权威库存隔离。整套回归通过，不能据此声称整场游戏帧率提升相同倍数。

原始结果保存在忽略目录 `dev_tools/output/deep_audit_20260908/production_*.json` 与对应日志。

## 战斗压力夹具

`dev_tools/tower_density_probe.gd` 加载正式塔防场景，使用现有植物注册、战斗查询、敌人仿真、原生物理与表现服务。初始密度为 100 玉米机枪 + 100 龙舌兰炮 + 100 木头加工站 + 100 橡木仓库，以及 240 基础原石虫 + 60 硬壳原石虫。

为了测量固定密度，夹具提高敌人与建筑血量、跳过放置距离/地形限制并停止不受支持地形的衰减；这不是正常通关平衡测试。初次记录为 400 建筑、300 敌人全数存活，16,522 节点、约 3,042 碰撞对，无窗口帧间隔 p95 21.33 ms。样本来自加入最新血条之前，不用于声称后续渲染收益。

联机与最终整合测量将在后续阶段补充；各阶段结果必须保留对应场景、引擎、窗口/无窗口和负载构成。
# 小地图显示查询的周期性开销（第二轮定位）

使用 Godot 原生本地脚本分析器 `-d --profiling` 对实际 400 建筑、300 敌人场景定位，
`TowerDefenseMinimapCanvas._sample_world_entities()` 是模拟协调器之外的主要周期性热点：
小地图每 0.1 秒采样敌人位置，先在敌人索引按稳定 ID 排序，再在统一查询层按类型和稳定 ID
重新排序。分析器开启时单次采样约 18–22 ms；此数字包含分析器额外开销，不作为玩家帧率。

增加明确的 `query_world_aabb_unordered_into()` 显示查询，与原有有序查询共用范围过滤、
活性判断和失效条目清理。小地图仅需无序完整集合；战斗查询保留原来的稳定顺序与排序后限额。
统一查询层也不再把敌人子集提前排序一遍。没有降低小地图采样频率或减少显示敌人。

`dev_tools/minimap_query_scaling_regression.gd` 使用 300 个真实 Enemy 场景和正式索引/查询层，
检查完整范围、局部范围、反向矩形、空/非有限范围、排除项、死亡、待销毁、跨范围移动，
以及默认查询按 ID 选择前 7 个目标，全部通过且正常退出。相同进程中 200 次查询：
旧双重排序 1145 ms，显示无序查询 75.9 ms（约减少 93.4%）。这是查询微基准，不代表整局加速比例。

同时补充了 `dev_tools/tower_density_probe.gd` 实战密度探针。原生 `Performance` 时间监视器
约一秒更新一次，其重复读数不能当作逐物理帧 CPU 耗时；探针分别报告墙钟帧间隔、监视器样本
和敌人协调器分阶段微秒累计。多人测量另见联网审计报告，单机与同机多进程数据应分开判读。
